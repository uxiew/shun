## 结论先说

- **伪造插件、跨 UID 调用（PLG04、PLG05）**：另一把密钥签的 rogue 直接绑定 echo 和 Mosh 插件，把 6 个 AIDL 方法（握手、ping、开会话、开 Mosh 会话、改尺寸、关会话）
  各调一次，12 次全部被插件拒绝，报 `SecurityException: 调用方 UID 10240 不是 top.xdwa.shun.debug`。反方向也测了：插件冒充别的插件给宿主回报事件，
  宿主两次都拒绝，报「调用方 UID … 不是 example.shun.fixture.echo」。
- **换签、多要能力、多要权限、API 升大版本（PLG11）**：用 `adb install -r` 覆盖安装，宿主每次都重新核验，开着的会话一律结束（`providerDied`），
  回到「待批准」「已拒绝」或「不兼容」，批准记录原样不动。**多要权限这一条修之前不成立**（第一个发现）。
- **撤销、卸载（PLG12）**：撤销批准后会话关掉、状态回到「待批准」；卸载后状态变成「安装包已不在设备上」。从头到尾另一个插件的会话都没受影响。
- **秘密（PLG14）**：真 Mosh 会话开着时，mosh-client 的命令行只有 `mosh-client 10.0.2.2 60101`，环境变量只有 `LANG MOSH_KEY_FD PATH TERM`，
  key 走的是 fd，不在命令行和环境变量里。崩掉插件后在 logcat 的全部缓冲区、dropbox、两个 App 的私有文件里搜测试密码、`MOSH CONNECT`、`MOSH_KEY`：都是 0 次。
  对照组：先往 logcat 写一个标记，能搜到，说明这几个 0 不是因为搜法失效。
- **外部入口（PLG04 宿主这一侧）**：release 包 `MainActivity` 被别的 App 带上 `cached_engine_id` 冷启动时，**修之前当场崩溃**（第二个发现），修完冷启动和运行中各发一次都不崩。
- **UU、RustDesk 的外部调用（UUR06、RDX02）**：伪造的 UU 回调、重复回调、nonce 不对的回调、别的 App 抢注回调地址，都没有被当成真的处理；
  RustDesk 平台桥拒绝了 25 种不合规链接，只把合规的那一条交给了指定的那个包。
- **生命周期（PLG08–PLG10、PLG16）**：echo 和真 Mosh 两边都跑了插件崩溃、强停、宿主崩溃。只有出事那个插件的会话结束，旁边的 SSH 标签一直是同一个对象、一直连着；
  之后远端一次都没有自己重新启动，宿主没有假装停干净。

## 两个发现（都已修）

### 1. 批准只绑能力不绑权限（107ed19）

**修之前**：批准记录（`shun.plugins.approvals.v1`）只存 pluginId、包名、证书、能力。插件更新后多申请一个权限
（比如 `own-session-ephemeral-secret`，也就是拿 Mosh 会话 key 的权限），宿主照样判「可用」，用户从没见过这个权限。
`plan/v3/STATUS.md` 原来把这条记成已知缺口「归 X11」。
**负对照**：把新加的检查临时去掉再跑设备测试（`../.toolchain/artifacts/x11-device-20261029-222830`），
测试在 `install-moreperms` 那一步一直等不到「待批准」，超时失败（`x11_trust_test.dart:203`，从 221 行调过去）。说明这个测试确实能抓到这个洞。
**修之后**：批准记录多存一个 `permissions`；descriptor 申请的权限超出批准范围就判 `NeedsApproval('插件申请了批准范围之外的权限，需要重新批准')`；
批准对话框多列一行「申请的权限：」；Mosh 会话 key 只有在批准记录**和**当前 descriptor 都带 `own-session-ephemeral-secret` 时才交出去。
旧记录没有这个字段，一律当「没批过任何权限」处理，所以 **10-29 之前批准过的 Mosh 插件升级后要重新批准一次**（所有者 10-29 同意这样做；已写进 `docs/user/README.md`）。
设备上：`echo-moreperms`（版本号、能力都和 echo-author 一样，只多一个权限）覆盖安装后，状态是「待批准 | 插件申请了批准范围之外的权限，需要重新批准」，
开着的会话 `providerDied`，批准记录里证书 `7feb5825…6e9d`、能力 `[terminal-session]` 都没变。

### 2. 别的 App 一条 Intent 就能让 shun 冷启动时崩溃（ce86d30）

**修之前**：`MainActivity` 必须导出（启动器要用），FlutterActivity 又会直接读 Intent 里的 `cached_engine_id`、`route`、`background_mode`、
`dart_entrypoint_args`、`enable_state_restoration`，还会读 data URI。在 release 包上执行：

```
adb shell am force-stop top.xdwa.shun
adb shell am start -W -n top.xdwa.shun/.MainActivity --es route /settings/plugins --es cached_engine_id evil -d 'https://evil.example/x'
```

结果 App 直接崩溃：`IllegalStateException: The requested cached FlutterEngine did not exist in the FlutterEngineCache: 'evil'`（崩溃日志原文在 `../.toolchain/artifacts/x11/plg04-before.txt`）。
本机装的任何 App 都能这样让 shun 一打开就闪退。App 已经在运行时再发一次不会崩，只会在日志里记一条找不到路由（现在没有命名路由；以后加了命名路由，别的 App 就能直接打开那一页）。
原来的代码只在收到 UU 回调地址时去掉 data，extras 一概不管。
**修之后**：`onCreate`、`onNewIntent` 把收到的 Intent 换成一个普通启动（`ACTION_MAIN`，只保留 category 和 flags）。本 App 自己从来不往这里放 extras
（通知点开用的就是启动器那条 Intent）。之所以整个换掉而不是逐个重写 `getCachedEngineId` 这类方法，是因为 Flutter 以后多读一个 extra 时逐个重写就会漏。
`SHUN_R39_AVD=shun-r39-a30 python3 tool/x11-device.py intents top.xdwa.shun`：冷启动、运行中各发一次带全部 5 个 extra 加 data 的 Intent，
进程都还在（pid 14328），crash 缓冲区里 0 条（`x11-intents-20261029-225632`）。正常从启动器冷启动、切回前台，首页都正常显示（「服务器视图」「添加连接」）。

## 没做的

- **真机：NOT_RUN**。所有者 10-29 定了 X11 只用模拟器。就算以后在真机上补测，也只装 echo 和 rogue；不装 fakeuu 和 fakerd，
  因为它们的包名和真的 UU、RustDesk 撞车，会把所有者手机上的真 App 覆盖或挡掉。安卓 12 及以后的系统对包可见性、前台服务的规则更严，这部分在 API 30 上测不到。
- **用 CI 正式密钥签的 release 包：NOT_RUN**。本机没有那把密钥。PLG15 用的是本机编的 release（见开头的「环境」）；
  「不认 debug 签名的插件」看的是构建模式，换成正式密钥不会改变这个判断，但发布前还是应该用正式的包再跑一遍 `x11-device.py intents top.xdwa.shun` 和 PLG15 那几步。
- **真的 UU、RustDesk**：没装。UUR06、RDX02 的「对方」都是测试包。

## 看到了、没有改的

- **`openMoshSession` 是在 API 1.0 里直接追加的，没有把 minor 升一版**。AIDL 里的注释自己就说了：调到旧插件不认识的方法时，Binder 不报错，
  void 方法看起来就像成功了。现在挡住它的只有权限这一道闸：只有声明了 `own-session-ephemeral-secret`、而且这个权限被批准了的插件才会被调。
  没有安全问题（调到了也只是会话打不开），所以没有改。下一个追加的方法必须升 minor。
- **「state 对、nonce 不对」的 UU 回调会把这次待处理的请求作废**。能拿到 state 的只有收到这次请求的 App（用户选中的那个「UU」），
  它能做到的只是让这次绑定失败，用户会看到「回调校验失败（nonce 不对），已作废」，重新发起就行。它绑不上设备，也拿不到任何东西。
  反过来如果不作废、留着继续等，攻击方就可以一直猜 nonce，所以现在这样是对的。
- **宿主被杀时 echo 报「关闭 0 个会话」**：不是泄漏。socket 先读到 EOF，会话已经自己关了，轮到 death recipient 时就没东西可关了。
  echo 的 fd 是 50→51：socket 5→4，anon_inode 4→6。会话用的 socket 是减少的；多出来的 2 个 anon_inode 具体是什么没查（只测了一次，没有反复杀宿主看它涨不涨）。已写进 `plugins/README.md` 的 hostkill 那一行。
- **mosh-client 段错误和插件被强停时，远端会留下 mosh-server**：和 X10 记录的一样，是 Mosh 本身的行为（客户端没来得及说再见），界面上如实说了，这次不重复讨论。
