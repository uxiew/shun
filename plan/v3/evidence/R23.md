# R23 恢复不重放与旧终端状态隔离

日期：2026-10-12。基线提交：`002cb00`。本轮是恢复路径的代码和本机隔离验证；没有安装到设备，没有连接所有者真实主机。

## 行为

- SSH/Telnet 恢复开始前先解除旧连接的输出与输入绑定。新 PTY 通过既有信任、路线、认证和目标核验后，Ghostty 在本地执行完整 VT 重置，清掉旧主/备用屏、滚动区、模式和残缺控制序列，随后才绑定新连接输出。失败时旧画面仍可作为历史查看，状态条明确显示断开/恢复受阻；旧字节不会混进新 shell。
- 恢复 PTY 打开到会话控制器正式接管标签之间，所有终端输出字节写入被直接丢弃，不排队。正式接管后才解开输入门。旧的按键、粘贴、启动命令和管理命令都不重发。Probe/Restore 继续沿用已有不执行 startup 的策略；tmux 只附着完整身份匹配的旧目标，缺失、同名重建或 server 重启时停下等待用户选择。
- 若旧连接曾把终端字节交给 SSH/Telnet 写入，断线时标记「结果未知」；写入传输层不能证明远端命令执行完毕。标记沿同标签恢复保留，在顶部提示用户核查远端，点「已核查」只清除本地提示、不发命令。终端内也显示提示；不保存输入内容、字节或命令到磁盘。此标记偏保守：终端协议回应也可能触发它，不能将其解读为某条具体命令失败或成功。
- 大输入框草稿仍只绑定原连接；恢复成新连接后不发送，用户必须显式点「改发到新连接」。关闭标签后的草稿留在本机内存的待处理区，App 冷启动不回放。

## 实际验证

`flutter analyze --no-pub` 无问题。主环境和 tmux 环境并行启动时，`flutter test --no-pub -j 4 --exclude-tags ai-cli-ssh-fixture --reporter expanded` **1162 通过、15 跳过、0 失败**。R55 的独立 SSH 用例须单独执行，原因见 `docs/shun/README.md`。

真实 OpenSSH 的 REG02/NET11 组最终 **5 条通过**：startup 和托管命令只执行初次，半行旧输入不在新 shell 执行；恢复前屏幕标记消失，新画面显示「结果未知」；恢复 PTY 接管前输入被丢弃、接管后才可发送；多行粘贴交给远端 `cat` 逐字节记录，断线后以文件实际字节为基准，恢复并手动按回车后文件不增加旧输入。第五条逐字节用例在上述全量后增补并独立通过，未冒称已纳入那次全量计数。

真实 tmux 2.4/2.7/3.0a/3.5a 的「附着、恢复、分离」组 **12 条通过**：四版本重新附着同目标、自动恢复、TMX04 同名重建拒绝、TMX05 server/用户/socket/主机身份变化拒绝、原会话不被杀、不踢其他客户端。Ghostty 真引擎测试核对重置后旧主/备用屏和残缺 OSC 消失、没有把重置字节写向新连接；终端状态条 widget 测试核对未知结果提示持久显示及「已核查」清除。R25 原有草稿测试在全量中通过，覆盖断线和新连接需显式改发；R22 的 LIFE04/LIFE05 旧证据仍在，未将它们重新记作本轮设备复测。

**边界**：NET11 与 REG04 在本机隔离 OpenSSH、真 Ghostty 和 widget 层按上述范围记 PASS；没有对 Android/iOS 设备再测这一候选。传输层无法知道命令是否执行、执行到哪一步，标记只能说未知；不提供 exactly-once 保证。不自动核查或重试有副作用命令。AIC03–AIC09 和 AI CLI 登录、启动、继续对话不在 R23 验证范围。
